# 演示脚本（课堂现场 5 分钟版）

> 目标：让老师在一次演示里同时看到 **哈希、排序、推荐算法** 三件事，且每一步都有可视化证据。

## 0. 启动（约 10 秒，release 已编译时）

```powershell
cd H:\web\zuoye\sf\campus-market
.\scripts\start.ps1
```

浏览器自动打开 `http://127.0.0.1:8080/`。终端会打印：

```
┌────────────────────────────────────────────┐
│  mini-redis 校园二手交易平台已启动          │
├────────────────────────────────────────────┤
│  Web UI : http://127.0.0.1:8080/            │
│  RESP   : 127.0.0.1:6380                    │
└────────────────────────────────────────────┘
```

同时另开一个终端连 CLI：

```powershell
.\target\release\mredis-cli.exe -p 6380
```

## 1. 开场：这不是一个「假」推荐系统（30 秒）

CLI 里敲：

```
127.0.0.1:6380> INFO
```

指着屏幕说：

- `# Dict` 段：`dict_buckets:128`、`dict_rehashing:0`、`dict_distribution:...`
  → 「这是我们自己写的哈希表，不是 `std::collections::HashMap`，桶分布可以直接看到。」
- `# Rec` 段：`rec_products:64`、`rec_users:8`、`rec_cooccur:...`
  → 「推荐引擎的倒排索引和共现矩阵就活在这个进程里。」
- `# Recent` 段：最近 50 条命令流
  → 「每一条命令都真实经过 RESP 协议解析、命令分发、写入内存。」

---

## 2. 哈希：桶分布与倒排索引（60 秒）

**Web「演示面板」页**：

1. 左侧 canvas 柱状图 = `dict_distribution`，横轴是桶编号，纵轴是链长。
   - 讲解：「64 个键散列到 128 个桶，绝大多数桶是 0 或 1，最长链 2——这就是链地址法 + 负载因子 1.0 扩容的效果。如果负载因子不控制，链会变长，查找退化成 O(n)。」
2. 点「插入 1000 个随机键」按钮（或 CLI 里 `for` 循环写），柱状图重新拉平。
   - 讲解：「扩容后桶数翻倍，链长重新摊平，平均查找 O(1)。」

**CLI 验证倒排索引**：

```
127.0.0.1:6380> SMEMBERS tag:自行车
127.0.0.1:6380> REC.STATS
```

→ 「`tag:自行车` 是一个 SET，`REC.STATS` 里的 `tags:37` 说明有 37 个标签桶，每个桶维护一份商品 posting list。查『自行车 + 运动』是两次 posting 求交，双指针 O(m+n)，不是全表扫。」

---

## 3. 排序：三种算法现场跑（60 秒）

CLI 或 Web 演示面板：

```
127.0.0.1:6380> REC.HOT 5
```

**Web「演示面板」→ 排序算法耗时表**（或跑 `mredis-bench.exe`）：

```
n=1000     three_way_quick  0.31 ms    std sort_unstable_by  0.19 ms    top_k(10)  0.05 ms
n=10000    three_way_quick  3.12 ms    std sort_unstable_by  1.88 ms    top_k(10)  0.41 ms
n=100000   three_way_quick 38.40 ms    std sort_unstable_by 22.10 ms    top_k(10)  4.02 ms
```

讲解要点（诚实，不吹）：

- 「三路快排在**大量重复键**时比标准库的二路快排更稳，因为等于枢轴的元素一次划分就定位了，不会退化成 O(n²)。校园二手市场里价格、成色重复很多，这是我们的针对性优化。」
- 「`top_k` 用大小为 k 的最小堆，O(n log k)，n=100000、k=10 时比全排序快近 10 倍——这才是生产环境取『前 10 个推荐』的正确做法。」
- 「我们**没有**在绝对速度上赢过 Rust 标准库的 pdqsort，那是工业级实现；我们赢在**算法可解释性**和**对重复键的鲁棒性**。这点写进了 ALGORITHMS.md。」

**市场页排序演示**：下拉选「价格从低到高」→ 列表重排；选「最新发布」→ 按 `created_at` 降序；选「热度」→ 按 `zset:hot`。

## 4. 推荐：三条路径（90 秒）

### 4.1 兴趣标签路径（内容推荐）

「为你推荐」页选 **用户 1（张三，兴趣：自行车/运动/健身）**：

- 卡片上每条推荐都带**中文理由**：
  - 「标签匹配：自行车、运动」
  - 「相似用户 3、8 也看过」
  - 「近期热度高（0.87）」
  - 「价格接近你的预算」
- 讲解：「最终分数 = 0.45×标签相似 + 0.25×协同过滤 + 0.10×热度 + 0.05×价格契合 + 0.15×同校区。权重是常量，在 `lib.rs` 顶部，可以现场改、重编译演示调参。其中同校区那项是校园场景特有的：同校区 ≈ 能当面交易。」

### 4.2 协同过滤路径

CLI：

```
127.0.0.1:6380> REC.EXPLAIN 2 1
```

返回：

```json
{"product_id":2,"score":0.6001,
 "parts":{"tag_sim":0.6667,"cf_sim":1.0,"hot_norm":0.1127,
          "price_fit":0.7759,"campus_fit":0.0},
 "weights":{"tag":0.45,"cf":0.25,"hot":0.1,"price":0.05,"campus":0.15},
 "matched_tags":["自行车","运动"],"similar_users":[7,2,4]}
```

讲解：「这是**可解释性**——不是黑盒。`similar_users:[7,2,4]` 说明用户 7、2、4 与张三有共同行为，
所以他们的收藏被推给张三。五个 `parts` 可以当场手算：
`0.45×0.6667 + 0.25×1.0 + 0.10×0.1127 + 0.05×0.7759 + 0.15×0 ≈ 0.6001`。
`campus_fit:0` 是因为这件商品在青山湖校区，而张三是前湖校区；同校区的商品会拿到 0.15 的满分加成，
并显示「同校区·可当面交易」徽章。共现矩阵只存 5 分钟窗口内的行为对，用 `(min,max)` 对称键，
空间从 O(n²) 降到 O(实际共现对数=57)。」

### 4.3 冷启动路径（**这是加分项**）

「为你推荐」页选 **用户 7（吴九，兴趣为空）**：

- 返回的全是热门商品，理由统一显示「冷启动·热门推荐」
- 讲解：「新用户没有行为、没有兴趣标签，协同过滤和标签匹配都失效。我们的降级策略是回退到热度榜——这是推荐系统里的标准做法，也是我们特意设计的一个演示场景。」

## 5. 交互闭环：行为如何改变推荐（60 秒）

1. 在市场页点开一个「乐器」类商品（比如「尤克里里」），点 **收藏**
2. 回到「为你推荐」，选**用户 4（赵六，兴趣：家具/宿舍/生活）** —— 之前他看不到乐器
3. 现在乐器类商品出现在推荐列表，理由变成「标签匹配 / 相似用户」
4. CLI 里看命令流：

```
127.0.0.1:6380> INFO
# Recent
recent_cmd:REC.TRACK 4 60 fav
recent_cmd:ZINCRBY zset:hot 5 60
recent_cmd:HSET product:60 favs 1
recent_cmd:LPUSH user:4:events {...}
recent_cmd:REC.FOR_YOU 4 10
```

讲解：「一次收藏 = 一串写命令：`REC.TRACK` 自身、商品计数器 `HSET`、热度 `ZINCRBY`、行为日志 `LPUSH`、权威收藏集合 `SADD`，并同步更新推荐引擎内存索引。全部经过同一套 RESP 命令分发，`REC.FOR_YOU` 立刻反映变化。」

## 6. 持久化：杀掉进程数据还在（40 秒）

1. `.\scripts\stop.ps1`
2. `.\scripts\start.ps1`（AOF 默认开启）
3. 刷新浏览器 → 刚才发布的商品、收藏行为都还在
4. **更强的一手**：在「详情」页用「编辑信息」改掉一个商品的价格、点「标记已售出」，再直接 `Stop-Process -Name mredis-server -Force`（强杀，不走 SHUTDOWN），重启后改动依旧在。

CLI 验证：

```
127.0.0.1:6380> DBSIZE
127.0.0.1:6380> GET meta:next_product_id
```

讲解：「AOF 是 append-only file，每条写命令以 RESP 格式追加。**每条命令立刻写穿到操作系统**，`appendfsync everysec` 只决定后台 fsync 的频率——所以哪怕进程空闲时被强杀，已确认的写命令也不会丢。重启时逐条重放；文件末尾如果有半条命令，加载时会截断到最后一个完整命令，不会启动失败。」

**如果老师追问「种子数据怎么也还在」**（这是个好问题，值得主动讲）：

> 「种子**只在持久化存储首次初始化时导入一次**，然后被写成 AOF 的全量快照，从此成为持久化数据的一部分——所以删掉或改掉种子商品，重启后不会被重新长出来。判断是否首次初始化靠 `<aof>.ready` 标记文件。启动顺序是『清空（可选）→ 读 AOF / 首次初始化导入种子并写快照 → 重放 AOF → 由键空间重建推荐索引』。推荐索引是键空间的**派生视图**（能从 `product:<id>` / `user:<uid>:events` / `user:<uid>:favs` 完整还原），所以重建而不是持久化。」

也可以现场演示「删了就是删了」：删掉一个种子商品，`SHUTDOWN` 再启动，它**不会**回来；再手动把 AOF 截断半条命令来演示重放截断容错。

## 7. 收尾：架构一页图（30 秒）

```
┌─────────────────────────────────────┐
│  Web UI（原生 HTML/CSS/JS，零依赖）  │
│  市场 / 详情发布 / 为你推荐 / 演示   │
└──────────────┬──────────────────────┘
               │ HTTP JSON（axum）
┌──────────────▼──────────────────────┐
│  mredis-web  REST 网关               │
└──────────────┬──────────────────────┘
               │ RESP2（自有协议栈）
┌──────────────▼──────────────────────┐
│  mredis-server（mini-redis）         │
│  ├─ 自研哈希表 Dict（链地址+增量rehash）│
│  ├─ 跳表 ZSet（span 实现 O(log n) 排名）│
│  ├─ 命令分发 76 条（含事务、停机）   │
│  └─ AOF 持久化 + 启动重放             │
│      └─ campus-rec 推荐引擎           │
│          ├─ 三路快排 / 二叉堆 top-k    │
│          ├─ 倒排索引（双指针求交）      │
│          ├─ Jaccard / 余弦相似度       │
│          └─ 共现矩阵协同过滤           │
└─────────────────────────────────────┘
```

一句话总结：

> 「我们用 Rust 从零实现了 mini-redis 的存储引擎和协议栈，再把一个**可解释的混合推荐算法**作为领域命令（`REC.*`）嵌进去。哈希、排序、推荐三种算法都在真实数据流上跑，不是 PPT 上的公式。」

## 附：常见提问预案

| 老师可能问 | 回答要点 |
|---|---|
| 为什么不用现成的 Redis？ | 课程要求「结合程序设计与算法思想」，用现成的就看不到哈希表扩容、跳表、AOF 重放这些实现细节。我们的目标是**可解释的算法实现**，不是生产级性能。 |
| 你的快排比标准库慢，意义在哪？ | 三路划分在**大量重复键**下不会退化；标准库 pdqsort 是工业级实现，我们不比绝对速度，比的是对数据分布的鲁棒性和可解释性。bench 表如实列出差距。 |
| 推荐算法会不会太简单？ | 是「简单推荐算法」的课程要求。但我们是**混合的**：内容（标签）+ 协同（共现）+ 热度 + 价格，还带**重排规则**（同卖家≤2、标签冗余降权）和**冷启动降级**，比单一 Jaccard 完整。 |
| 并发安全吗？ | 每个连接一个线程，共享 `Arc<Mutex<Database>>`。单机课程项目够用；文档里写了「换成 tokio 单线程 + 分片锁」的演进方向。 |
| AOF 会不会太大？ | 会，所以实现了 `BGREWRITEAOF` 重写：把当前键空间压成最小命令集。演示面板能看到 `aof_size` 变化。 |
| 数据规模？ | 64 商品 / 8 用户 / 76 行为是演示用；bench 里能跑到 10 万商品验证排序与索引的复杂度曲线。 |
